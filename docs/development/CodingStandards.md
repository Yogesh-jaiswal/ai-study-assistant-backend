# Coding Standards

## Overview

This document defines the coding standards followed throughout the AI Study Assistant backend.

The primary objective is consistency, readability, and maintainability rather than enforcing strict formatting rules. Contributors should prioritize writing code that is easy to understand, easy to extend, and consistent with the existing codebase.

When introducing new code, follow the conventions described below.

---

# General Principles

The project follows several core principles.

- Prefer readable code over clever code.
- Use meaningful and descriptive names.
- Keep responsibilities separated.
- Organize code into appropriate modules.
- Design components with future scalability in mind.
- Keep implementations consistent with surrounding code.
- Document architectural changes when introducing new patterns.

Consistency across the codebase is valued more than individual coding preferences.

---

# Naming Conventions

The project follows standard Python naming conventions.

| Element | Convention |
|----------|------------|
| Classes | `PascalCase` |
| Functions | `snake_case` |
| Variables | `snake_case` |
| Constants | `UPPER_CASE` |
| Private helpers | `_leading_underscore` |
| Python modules | `snake_case.py` |
| Documentation files | `PascalCase.md` |

Names should clearly describe their responsibility.

Avoid abbreviations unless they are widely understood.

---

# Project Organization

Each module should have a single responsibility.

Business logic should remain inside services.

Database access belongs inside repositories.

HTTP concerns belong inside routes.

Validation belongs inside validators.

Utility functions that are reused across multiple features belong inside `utils`.

Avoid placing unrelated functionality inside existing modules simply because it is convenient.

---

# Type Hints

Type hints are encouraged throughout the project.

In general:

- Public functions should include parameter type hints.
- Return types should be provided when practical.
- Complex helpers should also be typed.

Some exceptions are acceptable.

Examples include:

- avoiding deep dependency imports solely for typing
- avoiding unnecessary coupling between layers
- situations where typing becomes significantly more complex than the implementation itself

Routes should not introduce service-layer type dependencies.

Repositories should only reference SQLAlchemy models and should not depend on higher application layers.

Local variables generally do not require explicit type annotations.

---

# Documentation

Documentation should exist where it provides long-term value.

General guidelines:

- Most functions should include docstrings.
- Classes should generally include docstrings.
- Base classes should document their abstract behavior.
- Small private helper functions may omit docstrings.
- Simple methods inside well-documented classes may omit individual docstrings when their purpose is already obvious.

Documentation should explain responsibilities rather than implementation details.

---

# Imports

Imports generally follow the following order.

```python
# Standard library

# Third-party libraries

# Local project imports
```

This ordering is recommended for consistency but is not enforced rigidly.

Avoid unnecessary imports and remove unused dependencies whenever possible.

---

# Comments

Comments should be used sparingly.

Prefer descriptive naming over explanatory comments.

Comments are most useful when explaining:

- why something is implemented
- non-obvious implementation details
- architectural decisions
- complex workflows

Avoid comments that merely restate what the code already expresses.

When multiple related modules follow a common commenting style, newly added modules should follow the same convention.

Examples include logger initialization comments and short route descriptions.

---

# Logging

Application code should use the centralized logging system.

Avoid using `print()` inside the backend.

Logging should capture meaningful application events while avoiding excessive noise.

Sensitive information such as passwords, API keys, tokens, or private user data should never be logged.

The RAG evaluation package is the only exception, where lightweight console output is intentionally preferred over structured application logging.

---

# Error Handling

Errors should be raised where they occur.

Application components should not silently suppress exceptions.

Use the most appropriate exception type for each failure.

Custom exceptions should be preferred when they communicate business meaning more clearly than built-in Python exceptions.

HTTP responses are generated by the global error handling infrastructure rather than individual routes or services.

Celery workers manage failures independently and are not handled by the application's global HTTP error handlers.

---

# Dependency Rules

Dependencies should always flow in one direction.

```
Routes
    ↓
Services
    ↓
Repositories
    ↓
Database
```

The following rules should always be respected.

- Routes should not access repositories directly.
- Routes should not contain business logic.
- Services should not contain HTTP-specific logic.
- Repositories should not depend on services.
- Validators should remain independent of business logic.
- Shared utilities should remain generic and reusable.

Maintaining these boundaries keeps the architecture modular and easier to evolve.

---

# Consistency

New code should match the style of the surrounding implementation.

Examples include:

- logging conventions
- comment placement
- naming patterns
- module organization
- function structure

Avoid introducing alternative styles when an existing convention already exists within the same feature.

---

# Scalability

When implementing new functionality, consider future extension.

Prefer designs that allow new features to be added without modifying unrelated modules.

Reusable functionality should be centralized rather than duplicated across multiple features.

Premature optimization should be avoided, but unnecessary coupling should also be avoided.

---

# Documentation Responsibilities

Significant architectural or behavioral changes should be reflected in the project's documentation.

This includes updates to:

- architecture documents
- deployment guides
- development guides
- API documentation
- architectural decision records

Keeping documentation synchronized with the implementation is considered part of completing a feature rather than an optional task.
